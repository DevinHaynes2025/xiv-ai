## Founder user story

As the founder of XIV AI, I want XIV to become a governed enterprise operating intelligence layer that connects authorized business systems, continuously reconstructs the state of an organization, detects operational problems and opportunities, creates temporary specialist agent teams when needed, simulates possible interventions, explains recommendations to executives, executes only explicitly authorized actions, and learns from measured outcomes—so XIV functions as a Business Hospital for organizations without replacing human ownership, bypassing enterprise controls, or becoming an unrestricted autonomous operator.

Product loop:

```
ENTERPRISE SYSTEMS → AUTHORIZED CONNECTORS → BUSINESS DIGITAL TWIN → BUSINESS STATE
→ DETECT SYMPTOM → DIAGNOSE → FORM SPECIALIST TASK FORCE → SIMULATE OPTIONS
→ RECOMMEND TREATMENT → HUMAN EXECUTIVE DECISION → AUTHORIZED WORKFLOW
→ MEASURE OUTCOME → LEARN
```

## Architecture contracts (story §§1–102)

### 1. Compact enterprise architecture

Human executives sit above Executive Command, which sits above Guardian, which sits above the XIV Enterprise Control Plane. ERP, CRM, WMS, TMS, finance, HRIS, BI, and documents feed the Business Digital Twin. The Business Hospital Engine diagnoses, simulates, and forecasts. Agent task forces recommend. Humans decide. Authorized workflows execute. Outcomes return to learning. Production remains outside autonomous control.

### 2. XEOS — XIV Enterprise Operating System

**XEOS** is a governed intelligence and coordination layer. It does **not** replace ERP, CRM, WMS, TMS, HRIS, or finance systems.

Responsibilities: system integration, enterprise state reconstruction, cross-functional reasoning, workflow orchestration, decision support, simulation, evidence, human approval, outcome learning.

XEOS is not a company operator and not a merged super-system.

### 3. Enterprise System Registry

Create architecture for `xiv_enterprise_systems`:

`system_id`, `organization_id`, `universe_id`, `system_type`, `vendor`, `instance_name`, `capabilities`, `read_scope`, `write_scope`, `classification_ceiling`, `authentication_state`, `health_state`, `last_sync`, `status`.

Tenant-bearing. RLS required when implemented. **This document does not authorize migration execution.**

### 4. Supported enterprise domains

Initial classes: ERP, CRM, WMS, TMS, SCM, FINANCE, PROCUREMENT, HRIS, MANUFACTURING, ECOMMERCE, POS, DATA_WAREHOUSE, DATA_LAKE, BI, DOCUMENTS, COLLABORATION, TICKETING.

Supporting a category ≠ connecting an instance.

### 5. Enterprise connection states

`DISCOVERED` → `EVALUATING` → `CONFIGURED` → `SANDBOX` → `VERIFIED` → `AUTHORIZED` → `AVAILABLE` (also `DEGRADED` / `SUSPENDED` / `REVOKED`).

Only **AVAILABLE** systems may participate in authorized workflows.

### 6. XBDT — Business Digital Twin

**XBDT** is a structured representation of current operational state — customers, suppliers, inventory, orders, shipments, warehouses, facilities, employees, teams, machines, products, cash flow, budgets, projects, contracts, risks, workflows, service levels.

It is **not** a database dump.

### 7. Twin entity graph

Relationships, not isolated records. Example:

`CUSTOMER → ORDER → PRODUCT → INVENTORY → WAREHOUSE → SHIPMENT → CARRIER`  
and `SUPPLIER → PURCHASE ORDER → MATERIAL → FACTORY → PRODUCT`.

### 8. Temporal state

Every important object includes `current_state`, `previous_state`, `effective_at`, `observed_at`, `expected_state`, `forecast_state`. XIV must answer **what changed**, not only **what exists**.

### 9. Business Event Mesh

Normalized events (`inventory.low`, `shipment.delayed`, `supplier.failed`, `order.cancelled`, `payment.overdue`, `customer.churn_risk`, `machine.degraded`, `employee_capacity.low`, `budget.threshold`, `security.incident`) enter the 62H Event Mesh. 62K consumes; it does not rewrite 62H.

### 10. Business state reconstruction

`EVENTS + SYSTEM SNAPSHOTS + HISTORICAL STATE + HUMAN CONTEXT → XIV BUSINESS STATE`. Incomplete data must record **uncertainty**.

### 11. XBHE — Business Hospital Engine

Workflow: SYMPTOM → DIAGNOSIS → ROOT CAUSE → SEVERITY → TREATMENT OPTIONS → SIMULATION → RECOMMENDATION → HUMAN DECISION → TREATMENT → MONITORING → OUTCOME.

### 12. Business symptoms

Examples: stockout risk, late shipments, supplier instability, declining margins, churn, warehouse congestion, labor shortage, forecast error, excess inventory, cash-flow pressure, production downtime, software incident.

### 13. Symptom Detector

Inputs: metrics, events, forecasts, thresholds, anomaly models, human reports, historical comparisons. Output: `symptom_id`, severity, confidence, affected domain/value, evidence, recommended investigation. Detection ≠ diagnosis.

### 14. No automatic diagnosis from one signal

`LATE ORDERS` must not automatically become `WAREHOUSE FAILURE`. Competing causes: supplier delay, warehouse backlog, carrier delay, system error, demand spike, staff shortage, bad forecast.

### 15. Diagnostic task force

Activate only relevant roles via **62I Foundry** (reuse-first): Operations, Supply Chain, Finance, Data Analyst, Customer, Risk, Skeptic. Population Governor still applies. No unbounded team explosion.

### 16. Diagnostic workflow

SYMPTOM → COLLECT EVIDENCE → CREATE HYPOTHESES → TEST HYPOTHESES → RULE OUT CAUSES → ESTIMATE IMPACT → ROOT-CAUSE RANKING.

### 17. Root cause graph

Edges carry evidence. Example: late customer orders may branch to warehouse congestion (itself from labor shortage), carrier delay, or supplier delay.

### 18. Evidence strength

Every diagnosis must distinguish: observed fact, inference, prediction, assumption, human opinion, unknown. Do not blur them.

### 19. Treatment Engine

**XIV Treatment Planner** proposes: rebalance inventory, change reorder point, reroute shipment, increase temporary labor, change carrier mix, adjust supplier allocation, change production schedule, modify workflow, change pricing, pause promotion. Proposals until authorized.

### 20. Treatment restrictions

Explicit authorization required for: supplier cancellation, contract change, pricing change, employee action, major financial commitment, production shutdown, customer communication, external purchase.

### 21. Business Simulation Engine

Compose 62H/62I simulation. Input: CURRENT STATE, PROPOSED ACTION, ASSUMPTIONS. Output: EXPECTED IMPACT, UPSIDE, DOWNSIDE, COST, RISK, TIME, UNCERTAINTY. Simulation ≠ reality.

### 22. Treatment comparison

Compare options (including **do nothing**) on customer impact, cost, service level, margin, risk, time, operational feasibility.

### 23. Counterfactual analysis

Baseline: what likely happens if we do nothing. A recommendation should beat DO NOTHING on relevant business metrics — with uncertainty shown.

### 24. Executive recommendation contract

Every consequential recommendation contains: problem, business impact, root-cause hypothesis, evidence, options, recommended option, expected outcome, cost, risk, uncertainty, required approvals, next checkpoint.

### 25. XEC — XIV Executive Command

Answers: WHAT IS HAPPENING? WHY? WHAT WILL HAPPEN NEXT? WHAT SHOULD WE DO? WHAT WILL IT COST? WHAT IS THE RISK? WHO NEEDS TO APPROVE? WHAT HAPPENED AFTER THE LAST DECISION?

### 26. Morning Executive Brief

Example shape: 3 critical issues, 5 recommended actions, 2 requiring executive approval. All numbers must come from measured/model outputs. Night Shift (62I) may prepare the brief; it may not execute.

### 27. Executive storytelling

Prefer causal narrative over raw counts. Inventory fell 18%; demand +7%; supplier lead time +4.2 days; Product X projected to stock out in 11 days. Compose XIV “data tells a story” philosophy.

### 28. Business story timeline

Executives see causality over time (Monday supplier delay → Friday redistribution recommendation).

### 29. Enterprise Workflow OS

62H Workflow Engine becomes operational for: Supplier Risk Response, Inventory Rebalancing, Late Shipment Investigation, Customer Escalation, Security Incident, Budget Variance Review, Maintenance Incident. 62K does not rewrite 62H.

### 30. Workflow authority levels

`READ` / `ANALYZE` / `RECOMMEND` / `PREPARE_ACTION` / `REQUEST_APPROVAL` / `EXECUTE_BOUNDED_ACTION` / `CONSEQUENTIAL_ACTION` — each with separate permissions.

### 31. Read before write

Enterprise adoption phases: (1) READ (2) ANALYZE (3) RECOMMEND (4) APPROVED LIMITED WRITE. Do not start onboarding with unrestricted write access.

### 32. XEAG — Enterprise Action Gateway

Approved writes: WORKFLOW → ACTION REQUEST → GUARDIAN → HUMAN APPROVAL IF REQUIRED → ENTERPRISE ACTION GATEWAY → CONNECTOR → TARGET SYSTEM. Never AGENT → RAW CORPORATE PASSWORD.

### 33. Action contract

`action_id`, `organization_id`, `universe_id`, `system_id`, `actor`, `purpose`, `operation`, `target`, `before_state`, `proposed_change`, `classification`, `approval`, `budget`, `idempotency_key`, `status`.

### 34. Idempotent enterprise actions

Where technically possible, actions carry `idempotency_key` to reduce duplicate execution.

### 35. Consequential action classes

Payment, purchase order, pricing, contract, employee action, production shutdown, inventory write-off, customer refund, external communication. Default: **HUMAN APPROVAL REQUIRED**.

### 36. Autonomous low-risk actions

Future enterprises may authorize narrowly bounded operations (refresh dashboard, create internal ticket, update non-sensitive workflow status, schedule approved internal task, request fresh data). Only **explicitly configured** actions qualify. This park does not enable them.

### 37. Autonomous operations boundary

62K does **not** mean AI RUNS COMPANY WITHOUT HUMANS. It means: MONITOR, ANALYZE, COORDINATE, SIMULATE, RECOMMEND, EXECUTE ONLY WITHIN DEFINED AUTHORITY.

### 38. Human executive roles

### 39. Executive approval routing

### 40. Executive delegation

### 43. Procurement boundary
